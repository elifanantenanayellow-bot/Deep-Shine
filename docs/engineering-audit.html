01 Architecture overview

One Next.js 15 App-Router application. The interactive demo runs entirely in the browser against a deterministic seeded store; a PostgreSQL-backed production foundation lives alongside it. State flows one way: a single store context owns the data, pure selectors derive every view, and mutations are funnelled through typed actions.

Layering / separation of concerns

  • src/demo/data.ts — deterministic seed generator

  • app/(demo)/* — thin route pages, presentation only
  • standalone/* — offline single-file bundle (esbuild + shims)

04 Every real improvement made

Grouped by discipline. Each item is implemented, typechecked, and covered by a test or verified in the running app.

  • Extracted careTeam(data, patientId) — the access rule now has one definition, so the clinic and provider record views cannot diverge.
  • Extracted a shared MetricTile primitive; removed two identical local components.
  • Extracted loadOnDay() from the routing loop; separated the "which day" scan from the "which provider" ranking.
  • Kept pages thin: all derivations remain in pure, testable selectors — presentation stays in the page.
  • Team-hub thread list re-indexed to a single O(messages) pass (Map by thread) instead of two full scans per rendered row.
  • All derived views memoized with correct dependency arrays; the message index recomputes only when threads or messages change.
  • Long lists remain bounded (queues/ledgers sliced) — no unbounded renders introduced.
  • Team-hub: conversation search, "Sent" affordance on own bubbles, seeded the previously-empty DM threads so no conversation opens blank.
  • Calendar: provider filter box, keyboard day navigation (←/→/Home), filter-aware empty state, now-line, off-duty hatching, colour-coded walk-ins.
  • Consistent empty/loading states across the new screens (shared skeleton + EmptyState).
  • Compact currency inside the donut centre so large MGA totals never overflow the ring.
  • Routing documented end to end: earliest-day-wins, slot then caseload tie-break, stable seed-order final tiebreak → fully deterministic.
  • Edge cases verified by unit tests: provider off all week, empty pool, specialty with no provider, already-booked slot, lunch hour, full-day time off.
  • Seed correction (prior pass, retained): six-month revenue history now real; cost base derived from monthly revenue; stale invoices settle instead of ageing forever.
  • New unit layer via Node's built-in runner + tsx — zero new dependencies; wired into package.json and CI.
  • 13 unit tests over the pure selectors (routing, availability, finance, access rule).
  • 6 new E2E tests (message search, calendar filter, keyboard nav, calendar tenant-scoping); demo suite 103 → 109.
  • Offline single-file bundle exercised from file:// so the shipped artifact can't silently break.

06 Security review

Headline finding. The care-team access control on the customer record is a UI check against client-side state, not authorization. In the demo it correctly hides records from providers off the care team, but a real client could read the whole store. This must become a server-side rule before any real patient data exists.
FindingSeverityCurrentRequired in production
Record access enforced in the client onlyHighUI guard on /doctor/patients/[id]Server rule in the tenantDb() seam; explicit care-team relation
Ticket routing writes not transaction-guardedMedDeterministic in single clientReuse the serializable booking txn (F1 fix) so concurrent desks can't collide
No authentication on the demo surfaceBy designPersona switch, no authExisting JWT/RBAC foundation wired to these routes
Clinical notes: write path onlyMedAuthor recorded on writeAudit log on read as well as write (HIPAA-style)
Validation is client-sideMedForm checks + typed actionsZod at every server boundary (foundation already uses this)

Positive: strict row-level tenant scoping is respected everywhere in the new UI — the calendar, hub, costs and billing are all filtered to the flagship clinic, and an E2E test asserts no out-of-tenant provider leaks into the calendar.

What the tests actually prove

  • Routing: earliest slot chosen; lighter caseload wins ties; off/empty/wrong-specialty pools return nothing; result stays in-tenant.
  • Availability: lunch blocked, time-off removes the day, booked slots flagged taken.

  • Workflows: a ticket routes, books, notifies and lands on the calendar; cancelling frees the slot; a payment settles invoice + appointment together; notes/follow-ups persist across reload.

09 Production recommendations (not built — and why)

Each of these was requested. None is faked. Here is why it isn't in the demo, the architecture it needs, its complexity, and its priority.

Why not: the demo is a single browser tab with local state — two viewers cannot see each other, so "delivered/seen/typing" would be theatre.

Architecture: SSE (server→client) or WebSocket transport; a messages table with per-recipient read_at; a lightweight presence channel (Redis pub/sub or a hosted service such as Ably/Pusher). Optimistic send with server ack.

Complexity: Medium-High. Priority: After launch (category 3) — the async hub is useful without it.

Why not: no SMTP in a static/offline demo; the ticket records notifiedAt to model the event honestly.

Architecture: transactional email provider (Postmark/SES) behind a queue with retries + a bounce/complaint log; template + localisation (FR/MG).

Complexity: Low-Medium. Priority: Before first clinic (category 1) — an auto-routed ticket nobody is told about is worse than no routing.

Why not: there is no server in the demo; the guard is a UI affordance.

Architecture: an explicit care_team relation (provider × patient) rather than one inferred from appointment history; enforcement in the same tenantDb() seam as tenant isolation; 403 on mismatch; read-audit rows.

Complexity: Medium. Priority: Before first clinic (category 1).

Why not: a drag that doesn't survive reload or coordinate across staff is a trap; it implies a guarantee the demo can't keep.

Architecture: pointer-based DnD (dnd-kit) writing through the same booking mutation, which must run in the serializable transaction + exclusion constraint that already guards double-booking; optimistic move with rollback on 409.

Complexity: High. Priority: After launch (category 3).

Why not: the demo mutates an invoice in place; a real ledger must be append-only and reconcilable.

Architecture: immutable payment-ledger table (charges, refunds, adjustments as separate rows); tax as a configurable line per tenant; partial payments as multiple ledger entries summing to the invoice; nightly reconciliation against MVola/Orange statements.

Complexity: High. Priority: Category 2 (before paying customers) for MVola; refunds/taxes category 3–4.

Present today: revenue vs cost, margin, six-month trend, category breakdown, no-show rate, top providers, revenue by method.

Not built: forecasting and conversion funnels require a warehouse and event tracking, not derived store reads.

Architecture: event stream → columnar store (or Postgres materialised views) → scheduled rollups; a forecast is a simple seasonal model over ≥12 months of real data (which a demo doesn't have).

Complexity: Medium. Priority: After launch (category 3).

Why not: no object storage or virus scanning in a client demo.

Architecture: signed-URL uploads to S3-compatible storage; metadata rows scoped by tenant + care team; AV scan on ingest; the notes model already carries authorship and can host version history.

Complexity: Medium. Priority: After launch (category 3).
